# 2026-07-31 Windows neonctl 一次性命令 CPU 自旋事故

## 1. 问题现象

在 Windows PowerShell 中直接执行 `neonctl@2.30.1` 的一次性命令 `dist/cli.js --help` 后，命令未正常结束，进程链表现为 `cmd.exe -> node.exe`。异常 Node 进程持续占用一个 CPU 核心，未提供监听端口，也没有产生可用的命令输出。

首次可信信号来自进程 CPU 采样：Node PID `22320` 在 5 秒内累计增加 `5.66` 秒 CPU 时间，累计 CPU 时间为 `7891.41` 秒。这说明问题不是正常的网络等待或交互式认证，而是进程在本地持续自旋。

## 2. 实际根因

故障根因是 Windows 上 `neonctl@2.30.1` 的 CLI 启动链在一次性命令场景中发生 Node CPU 自旋。该行为发生在 `--help` 这种不依赖项目配置、云端资源或数据库连接的命令上，因此不能归因于 Neon 组织、数据库权限、网络连接串或本仓库业务代码。

## 3. 关键误导点

- `neonctl` 的名称容易被误认为是 Neon 官方当前推荐的 CLI；它不是本项目允许使用的工具。
- 一次性命令没有返回，不应先反复等待、重试或继续执行其他 `neonctl` 子命令。CPU 采样已经能区分“慢”与“自旋”。
- 不能因为没有端口监听就认为进程没有影响。该事故的风险是无输出的 CPU 长时间占用和遗留 Node 进程。

## 4. 有效修复

1. 使用受限的 `candidate-stuck-one-shot` 门禁识别异常的一次性 Node 子进程，仅停止确认自旋的子进程；不要按映像名批量终止所有 `node.exe`，避免中断正在运行的开发服务、构建或其他 agent。
2. 所有 Neon 云端资源操作统一改用官方 `neon` CLI，并且只在已安装、已认证且用户明确授权后执行。
3. 数据库迁移、同步和验证优先使用 Vercel 项目现有环境变量取得的连接串配合项目脚本或标准数据库客户端执行；连接串、密码和 token 不得写入仓库、报告或终端记录。
4. 在仓库中保留 `scripts/guard-neon-cli.ts`，由根本地 `tsx` 执行；`turbo.json` 将该守卫建模为构建、类型检查和文档构建的依赖。守卫命中 `neonctl` 时必须失败，阻止它进入本地构建、类型检查、文档构建和 CI。

## 5. 验证方式

- 对异常进程执行 5 秒 CPU 增量采样，确认命中自旋门槛后再停止；停止后重新采样，Node CPU 增量应为 `0`。
- 确认父 `cmd.exe` 与上层 Node 包装进程会在异常子进程停止后退出。
- 运行 `pnpm exec tsx --check scripts/guard-neon-cli.ts`，确认守卫脚本语法有效。
- 运行 `pnpm run neon:guard`，确认当前仓库未检出可执行的 `neonctl` 引用；CI 在依赖安装后执行同一守卫。

## 6. 后续约束

- Windows 环境禁止直接执行、安装后调用或在 `package.json`、脚本、工作流中引入 `neonctl`。
- 需要操作 Neon 时，先确认目标是仓库关联的既有 Neon 资源，再使用官方 `neon`。禁止因命令示例或查询不完整而创建第二个同用途 project 或 database。
- 若 `neon` 本身出现超时或退出异常，先采集命令行、父子进程和 CPU 增量证据；不要退回 `neonctl` 作为替代方案。
- 每次新增自动化命令时均须通过 `pnpm run neon:guard`，并在代码审查中检查是否绕过该守卫。
