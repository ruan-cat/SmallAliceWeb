# 2026-08-24 Agent Browser 本地 Chrome 与路由验收复盘

## 1. 结论

这次使用得不好，主要责任在执行方式，而不是把所有问题归咎于 `agent-browser` CLI。

全局 `agent-browser` 技能正确要求先加载 CLI 的 `core` 指南；该指南已经提供 snapshot → action → re-snapshot、条件等待、`doctor`、CDP、会话隔离和复杂 `eval` 的安全入口。我没有把这些要求落实成验收前置条件，导致先后出现错误路由、浏览器启动链路不清和低质量视觉证据。

技能仍有一个 Windows 适配缺口：复杂 `eval` 的示例以 Bash heredoc 为主，没有给出 PowerShell 等价写法或建议直接使用 `-b`。但该缺口不足以解释把用户给定 URL 自行改写、在 `doctor` 失败后继续使用默认启动器、或把资源加载当作视觉通过。

## 2. 已观察到的失败链路

|          事件          |                             实际行为                              |                  影响                  |          责任判断           |
| :--------------------: | :---------------------------------------------------------------: | :------------------------------------: | :-------------------------: |
|      验收标准过窄      |               只检查 `img.naturalWidth` 和文字可见                |    漏掉 EMF 的重复图层、错位和裁断     |          执行错误           |
|      本地路由改写      |           擅自去掉用户给定 `.html`，并百分号编码后访问            |    VitePress 返回 404，浪费调试时间    |          执行错误           |
|     默认启动器失败     | 指定本机 Chrome 后遇到 exit code 3 / daemon EOF，未立即收敛到诊断 |       浏览器来源和证据链一度不清       |          执行错误           |
| PowerShell inline eval |             将 `\|\|`、箭头函数和对象字面量塞进命令串             | 生成 3 个 0 字节脏文件并造成 eval 失败 | 执行错误 + Windows 示例缺口 |
|       EOF 被弱化       |      `agent-browser` 返回 daemon EOF，但后续子命令碰巧仍完成      | 结果可用但过程不可靠，不能作为标准流程 |          执行错误           |

## 3. 路由 404 的根因

用户给出的本地页面路径本身就是验收契约：

- `/docx/插件详细手册/19.控件/关于技能窗口块元素.html`
- `/docx/插件详细手册/2.战斗/关于战斗活动镜头.html`
- `/docx/插件详细手册/20.标题/关于全自定义标题界面.html`
- `/docx/插件详细手册/21.管理器/关于素材库.html`
- `/docx/插件详细手册/21.管理器/数据存储的载体.html`

我错误地把静态站生产 URL 的“是否带 `.html`”当成可以自行规范化的细节，先访问了去扩展名和百分号编码的变体。VitePress 本地 dev server 在该项目的动态路由/文件发现状态下没有把这些变体等价处理，于是落入 404 页面。

正确做法是：用户给出 URL 时，先原样拼接 `http://127.0.0.1:<port>` 并打开；只有该精确 URL 失败后，才记录 HTTP 状态、VitePress 路由配置和实际 Markdown 文件路径，提出受证据约束的替代路径。不能在验证前自行“优化”URL。

## 4. 浏览器启动与控制问题

### 4.1 错误做法

我最初依赖 `agent-browser --headed` 的默认启动器，又在失败后零散叠加 `--executable-path`。`agent-browser doctor` 已报告 Chrome 早退、未写入 DevToolsActivePort；按技能要求此时应该停止普通页面操作，先处理 daemon/启动问题。

### 4.2 最终可用做法

为满足“本机 Google Chrome”要求，最终流程是：直接启动 `C:\Program Files\Google\Chrome\Application\chrome.exe`，使用独立临时 profile 和明确的 `--remote-debugging-port`，再由 `agent-browser --cdp <port>` 接管。

该方案的优点是可证明浏览器来源、避免碰触用户日常 profile、允许可见窗口验收；缺点是需要显式管理本次启动的 Chrome 进程和 profile 目录。后续应把它固定为 Windows 本地视觉验收的首选路径，而不是在默认启动器失败后才临时改用。

### 4.3 新建浏览器失败不等于现存会话不能做视觉验收

`agent-browser doctor` 的 Launch test 失败、默认 daemon EOF 或 typed MCP `open` 无响应，只能证明**新建或接管链路异常**；它们不能证明当前已有的 Agent Browser 标签页无法读取客户端 DOM、枚举 `<img>`、滚动元素或保存截图，更不能被误判为 VitePress SSR 让图片不可见。

2026-08-24 的复验已证明这一点：虽然新建 Chrome 的 Launch test 失败，现存会话仍能打开用户原样 URL、返回页面标题、枚举 26 张客户端图片、将 `关于高级角色肖像-003.png` 滚入视口并保存截图。人工判读该截图确认图内浅色文字和细线在白底上低对比，说明 Agent Browser 可以发现真实渲染缺陷，而不是只能统计 `naturalWidth`。

因此，遇到启动诊断失败时必须先区分两类状态：

1. **现存会话仍响应**：先以最小探针验证 `get url`、`get count img`、图片枚举、`scrollintoview` 和 `screenshot`；探针成功后继续用该会话完成目标图视口验收，并在证据中写明新建链路仍有风险。
2. **现存会话也不响应**：才停止普通页面操作，先处理 daemon/CDP 启动问题；不得把无截图、无 console 的失败状态包装成“SSR 看不到图片”或“页面不可验收”。

## 5. 视觉验收链路的错误与修正

首次验收只证明了资源没有坏链，不能证明 EMF 图形正确。正确链路应同时包含以下三层：

|    层级    |                           必须检查                           |        不能替代什么        |
| :--------: | :----------------------------------------------------------: | :------------------------: |
|   转换层   |        子包 Vitest、真实 EMF fixture、GDI+ frame 尺寸        |      不能替代页面视觉      |
| 本地页面层 | 本机 Chrome 打开用户原始 HTML 路径、滚到目标 `img`、视口截图 |      不能替代生产容器      |
| 生产页面层 |       同一 Chrome 路径和截图复验、Vercel SHA/EMF 统计        | 不能用旧部署或资源请求替代 |

这次最终修复把 mapping EMF 从错误的 816×208 `rclBounds` 恢复到 Windows GDI+ 的 841×335 frame，并撤销了重复扣减 `rclBounds.left/top`。本机 Google Chrome 和生产 Google Chrome 对五个页面的截图都确认：标题不再双层偏移，战斗图不再有第二套深色图层，素材库、技能窗口和数据存储图不再裁断或显示占位符。

### 5.1 覆盖范围修正

该结论只覆盖当时的五个指定页面。用户随后人工检查仍发现大量其他 EMF PNG 有乱码和错位，因此不能把这五页通过外推为全量质量合格。后续必须建立大覆盖率或全量视觉审计，并按乱码、文字错位、图层重复、裁断和占位符建立真实 EMF/GDI+ 回归门禁。

## 6. 后续标准操作

1. 启动本地 dev server 后，先用用户原样 URL 打开一页，读取标题确认不是 404。
2. Windows 上优先显式启动本机 `chrome.exe` 的临时 profile，再用 `--cdp` 接管；默认启动器仅作为可验证成功的备选。
3. 每次导航后执行 `wait --load networkidle`、读取标题、统计图片数量和未加载图片；任何 `EOF`、连接拒绝或 `doctor` 失败都视为链路失败，不可用“后续命令似乎成功”掩盖。
4. 视觉缺陷必须 `scrollintoview` 到目标图后截图，并由模型实际查看截图；全页缩略图和 `naturalWidth` 只能当辅助证据。
5. PowerShell 中不使用复杂 inline `eval`。复杂脚本使用 CLI 支持的 stdin/base64 路径，或拆成 `get count`、`get attr` 等简单命令；执行后立即检查 `git status`。
6. 生产验收记录必须写明：浏览器可执行程序、CDP 端口/会话类型、精确 URL、截图路径、部署 ID、提交 SHA、图片加载统计与视觉结论。
7. 遇到 `doctor` 的 Launch test 失败时，先对现存会话运行“图片枚举 → 目标图滚入视口 → 截图 → 人工判读”的最小探针；只有探针也失败，才能将视觉验收标为控制链阻塞。不得把 SSR、路由、资源加载或新建浏览器失败混为同一根因。

## 7. 需要补齐的技能改进

建议后续更新全局 `agent-browser` 技能或其 Windows 附录：

- 给出 PowerShell 安全传递复杂 `eval` 的可复制方式，避免 Bash heredoc 示例被生搬硬套。
- 增加“用户给定 URL 不得自行去扩展名、编码或改写”的视觉验收规则。
- 增加 Windows 本机 Chrome CDP 接管模板，以及默认启动器 `doctor` 失败后的明确止损路径。
- 将视觉验收最小证据固定为“目标图视口截图 + 人工判读”，明确 `naturalWidth` 只证明加载状态。
- 增加“新建浏览器与现存会话分离诊断”章节：先检查已有标签页是否可截图，再决定是否需要修复 launch/CDP；明确 VitePress SSR 不会阻止真实 Chrome 会话读取客户端图片。
