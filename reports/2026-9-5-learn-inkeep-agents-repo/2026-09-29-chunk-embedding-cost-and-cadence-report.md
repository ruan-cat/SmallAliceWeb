# 2026-09-29 chunk embedding 模型、额度消耗与批量频度分析报告

> 本报告基于 2026-09-29 三次 CLI 脚本真实运行（本会话）的实测数据 + Cloudflare 官方定价文档查证，回答四个问题：embedding 用什么做、消耗多少 Cloudflare 免费额度、合理批量频度、写库行为与时间成本。

## 1. 一句话结论

> **当前用 Cloudflare Workers AI 的 `@cf/baai/bge-m3`（1024 维）做向量化**；免费额度 **10,000 Neurons/天 ≈ 930 万 input tokens/天**；本项目**单次全量同步约消耗 1,500~2,000 Neurons（日额度的 15~20%）**，三 profile 全量参数评估约 5,200 Neurons（约一半日额度）；**合理频度 = push 驱动增量为主（常态近零消耗）+ 每日兜底 1 轮哈希对比（≈0 消耗）+ 全量重建单日 ≤1 次**——免费额度内全部够用，无需付费。

## 2. chunk embedding 现状：用什么做

| 项目           | 取值                                                                                                                         | 出处                                             |
| :------------- | :--------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------- |
| 模型           | `@cf/baai/bge-m3`（多语言，上下文窗口 60k token）                                                                            | `cloudflare-embedding.ts:2` + spec Requirement 6 |
| 向量维度       | 1024 维 dense（写入前校验：必须 1024 维有限数值，否则事务前失败）                                                            | `CLOUDFLARE_EMBEDDING_DIMENSIONS`                |
| 调用端点       | Cloudflare REST：`POST /accounts/{accountId}/ai/v1/embeddings`（OpenAI-compatible 形态，body 为 `{model, input: string[]}`） | `cloudflare-embedding.ts:42-44`                  |
| 单批上限       | provider 层硬校验 ≤100 条；sync 主链路按 100 条/批                                                                           | `CLOUDFLARE_EMBEDDING_BATCH_SIZE`                |
| 批内顺序       | 返回按 `index` 排序校验，必须与输入顺序一一对应                                                                              | `orderEmbeddingData`                             |
| 自适应容错     | 评估脚本遇 400/413 自动二分批重试（`adaptive-embedding-batch`）                                                              | `embedBatch`                                     |
| embedding 输入 | `buildEmbeddingText`：确定性标题路径上下文 + 正文；图片 URL MUST NOT 进入输入                                                | spec Requirement 6                               |

**两套批次参数（容易混淆，务必分清）**：

| 链路                                              | 批大小        | 说明                                           |
| :------------------------------------------------ | :------------ | :--------------------------------------------- |
| sync 主链路（rag:sync / POST /v1/knowledge/sync） | **100 条/批** | spec Requirement 6 上限                        |
| 评估脚本（run-parameter-evaluation 等）           | **25 条/批**  | `DEFAULT_EMBEDDING_BATCH_SIZE = 25`，请求数 ×4 |

### 3.4 本会话实际消耗复盘

2026-09-29 当天实际执行：全量 parameter 评估一轮（≈5,200）+ real 评估一轮（≈11）+ GA 首跑（0 文件，0）+ 一次 502 中断重跑（约 2,850/6,737 chunks 后中断，约消耗 750 后重跑）——**当日总消耗约 6,000~7,000 Neurons，仍在 10,000 免费额度内**（这也是当晚最后一次 parameter 重试能通过的原因；若再重跑一次 parameter 就会撞顶报错）。

## 4. 合理批量 chunk embedding 频度建议

### 4.1 频度设计依据

- **增量语义兜底**：内容哈希 + profileVersion + embedding 模型版本未变 → 自动跳过（spec Requirement 3），增量轮 embedding 成本 ≈ 变更文件 chunk 数。
- **实测更新节奏**：12/60 天活跃（plan 18.6 S2 拷问）——常态下绝大多数轮次零变更、零消耗。

### 4.2 建议频度矩阵

| 场景                                               | 建议频度                                    | 单次消耗                            | 依据                                          |
| :------------------------------------------------- | :------------------------------------------ | :---------------------------------- | :-------------------------------------------- |
| **push 驱动增量同步**                              | 每次文档变更即触发（事件驱动，不限频）      | ≈0~11 Neurons/次                    | 成本与变更量成正比，事件驱动最省              |
| **schedule 每日兜底**                              | 1 次/天（现 UTC 18:30）                     | **0 Neurons**（无变更轮纯哈希对比） | 防漏兜底，空转成本为零                        |
| **全量重建**（profile/embedding 模型变更时才需要） | 触发时单日 ≤1 次，低峰执行                  | ≈1,600 Neurons                      | 单次 < 20% 日额度；避免与其他评估同日叠加撞顶 |
| **parameter 参数评估**（三 profile 全量）          | 按需（仅调整 chunk profile 时），单日 ≤1 轮 | ≈5,200 Neurons                      | 占日额度一半，是最大的消耗项                  |
| **real/dry 评估**                                  | 随时可跑                                    | ≈0~11 Neurons                       | 可忽略                                        |

### 4.3 频度红线

1. **单日 Neurons 总预算 ≤ 10,000**（免费额度）；全量重建与 parameter 评估**不要同日叠加**（1,600 + 5,200 = 6,800，虽不超但余量吃紧，再叠加任何真实 LLM 调用同账户 Neurons 会共用额度池）。
2. **批大小保持 sync=100**：请求数最少（290 文件全量仅 68 批）；评估脚本 25/批可按需调大（413 时自适应二分兜底），但非瓶颈不必动。
3. **避开 UTC 00:00 前后**：额度重置边界，重置前最后一批全量 embedding 可能撞顶失败（本会话已实证 502 类瞬时故障需要重试余量）。
4. **瞬时故障重试纪律**：Cloudflare 偶发 502/429（本会话实测 1 次），等待 90s 重试通过；脚本无自动重试，人工重跑即可，无需为此加复杂度。

## 5. 写库行为与效率

### 5.1 每次 chunk embedding 会写 Neon 吗？

| 链路                                    | 写什么表                                                                                                  | 写库时机                                                                                                                                                                                                                                         |
| :-------------------------------------- | :-------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **sync 主链路**（rag:sync / HTTP 同步） | **真实写三张表**：`documents`（幂等索引）、`chunks`（向量 + 结构化元数据）、`knowledge_sync_runs`（审计） | **每文档一个事务**：先完成该文件全部 batch embedding 与 1024 维校验 → 单文档事务内 `DELETE 旧 chunks` + `INSERT documents` + `INSERT chunks` 批量多值语句；轮末 UPDATE sync_runs。**embedding 生成与写库解耦**：单文档重建失败时旧版本保持可检索 |
| **评估脚本**（run-parameter 等）        | **不写真实表**：写会话级 TEMP TABLE（连接关闭自动消失）+ 评估完成后 `evaluation_runs` 落一行              | 批量 INSERT（25 行/语句）+ 完成后建 HNSW 索引                                                                                                                                                                                                    |
| **advisory lock**                       | `NITRO_SYNC_DATABASE_URL`（non-pooled 专用连接）持有，防并发同步                                          | 与写库连接分离                                                                                                                                                                                                                                   |

### 5.2 写库效率（实测 + 结构分析）

| 操作                                                     | 实测/估算                                                             | 说明                                                                                                                                 |
| :------------------------------------------------------- | :-------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------- |
| 评估 TEMP TABLE 批量写（6737 行，25 行/语句 × 270 语句） | **秒级**（embedding 占绝对大头，写库时间可忽略）                      | 实测：embedding 完成后建 HNSW 索引 + 三 profile 检索评估在数十秒内完成                                                               |
| 真实 sync 写库（290 文档全量）                           | **估算 1~3 分钟量级**（290 个单文档事务 × Neon pooled ~10-50ms/语句） | **待实测**：CI 内无知识源（partial 0 文件），真实全量写库效率待知识源分发方案落地后补测；理论瓶颈不在写库而在 embedding（见第 6 节） |
| `evaluation_runs` 落一行                                 | <1s                                                                   | 本会话三行真实落库实测                                                                                                               |

**效率关键结论**：embedding 网络调用占整条链路 **>95% 时间**，Neon 写库（pooled、批量多值 INSERT、单文档事务粒度）不是瓶颈。写库的正确性保障（事务替换 + 写前校验 + 失败保旧）比极致写速更重要，当前设计无需优化。

## 6. 脚本执行速度与时间成本（本会话实测）

| 脚本                        | 规模                                                                                    | 实测耗时                                       | 吞吐                                                                                   | 备注                                             |
| :-------------------------- | :-------------------------------------------------------------------------------------- | :--------------------------------------------- | :------------------------------------------------------------------------------------- | :----------------------------------------------- |
| `run-rag-evaluation`（dry） | gold-set 1 条记录，0 provider 调用                                                      | **秒级**                                       | —                                                                                      | 含 evaluation_runs 落库                          |
| `run-real-evaluation`       | 10 题真实 embedding + 检索 + HNSW/exact 对比                                            | **~1 分钟**                                    | ≈30 次单条调用                                                                         | 顺带产出 hnsw 与精确扫描一致性对比               |
| `run-parameter-evaluation`  | **3 profile × 全量 chunk**（6737 + ~6200 + 5949 ≈ 18,900 chunks，25/批 ≈ 748 批次请求） | **18m30s**（含 90s 重试等待，纯执行 ≈17 分钟） | **≈1s/批（25 条）≈ 25 chunks/s ≈ 1,450 chunks/min**；单 profile 6737 chunks ≈ 4.5 分钟 | 含三 profile 检索评估 + HNSW 索引重建 + 精确对比 |
| 首次运行撞 502 时的进度对照 | 2850/6737 chunks 处中断                                                                 | ≈4 分钟                                        | 与 ≈1s/批 吻合                                                                         | 瞬时故障，等待 90s 重试通过                      |

**时间成本结论**：

- **全量同步**（sync 100/批）：纯 embedding 约 **68 批次 ≈ 2~3 分钟**（大批次单批延迟略高），加写库 1~3 分钟 → **全量重建端到端 5 分钟量级**，完全可接受。
- **当前速度瓶颈**：评估脚本的 25/批串行请求。若追求评估提速，把 `DEFAULT_EMBEDDING_BATCH_SIZE` 提到 100 可把请求数降 4 倍（评估耗时约 5 分钟）；但评估是低频操作，**不建议为此改动**（简洁优先）。
- **单批延迟 ≈1s**（25 条）：Cloudflare 端 GPU 推理 + 网络往返，国内网络环境下属正常水平。

## 7. 边界与不确定性声明

1. **token 估算为近似值**：bge-m3 tokenizer 实际切分未逐条验证，1.4~1.9M tokens 区间基于 1~1.5 chars/token 经验值；Neurons 换算随之浮动 ±15%。精确值可在 Cloudflare Dashboard 的 Neuron 用量页对照（跑一轮全量 sync 前后看差值）。
2. **真实全量 sync 写库效率未实测**：CI 内知识源缺失（partial 0 文件），写库效率为结构分析估算；知识源分发方案落地后随首次真实全量同步补测。
3. **Workers AI 免费/付费请求速率限制（RPM）**：官方定价页未在本次查证中给出明确数值；实测 25/批串行 ~1s/批 未触发限流。若未来并行化 embedding 请求，需先实测限流阈值。
4. **计费数字时效**：bge-m3 = 1,075 Neurons/M tokens 来自 2026-09 官方定价页与两个独立来源交叉一致；Cloudflare 价格可能调整，长期使用前以官方 pricing 页为准。
5. **多模型同池**：Neurons 是账户级共享额度——同账户下的聊天模型（anthropic/openai 走自有 key 不占 Neurons）、其他 Workers AI 调用会共同消耗日额度，规划频度时需按账户全局视角盘点。

## 8. 行动建议汇总

1. **不需要任何付费动作**：当前频度下（增量为主 + 每日兜底 + 偶发全量），免费额度绰绰有余。
2. **parameter 评估是唯一大户**（≈52% 日额度/轮）：保留「按需、单日一轮」纪律即可。
3. **全量重建与评估错峰**：不同日执行，避免撞 10k 顶。
4. **知识源分发方案落地后**：补测真实全量 sync 的写库效率与端到端耗时，回填本报告第 5.2 节。
5. **监控入口**：Cloudflare Dashboard → Workers AI → Neuron 用量（每日重置），建议全量重建前先看一眼当日已用量。
